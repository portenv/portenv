# Milestone 0.2: toolbox image

Date: 2026-10-07

## What exists now

- `images/toolbox-node`: one Dockerfile for arm64 and amd64, with pinned inputs (base and builder images by digest, Node 22 by checksum, Claude Code's apt key by fingerprint).
- `portenv-agent init` as PID 1: checks `work` (uid 1000), checks or creates the home, replays `apt-packages.txt`, serves readiness on a root-only socket, reaps orphans, stops the box cleanly.
- A new box's home comes from the skeleton only with `PORTENV_INIT_HOME=1`; a box whose home storage is missing fails loudly instead of starting empty (ADR 0003).
- `images/toolbox-node/test.sh`: 30 checks against a built image. CI (`.github/workflows/images.yml`) runs it on native amd64 and arm64 runners and publishes the multi-arch manifest on `toolbox-node/vN` tags.

## Demo

```sh
make image-test
docker run -d --name demo -e PORTENV_INIT_HOME=1 -v demo-home:/home portenv/toolbox-node:dev
docker exec demo portenv-agent ready          # READINESS_STATE_READY: ready
docker exec -it -u work -w /home/work demo bash -l
```

## Notes

- Local result on an Apple silicon Mac (Docker Desktop, linux/arm64): image 1.36 GB, build about 5 minutes uncached, all 30 checks pass in 34 seconds.
- CI on PR #3: the Images workflow built the image natively on amd64 and arm64 runners and all 30 checks passed on both.
- The Images workflow runs only when image-related paths change, so its jobs are not required checks on `main` (a required check that never reports would block docs-only pull requests).
- `docker exec` appears only in the Phase 0 test script; Portenv itself never uses it as an access path.
